# ADR-047 Amendment (2026-05-03): Defer Tool-Call BlockStart to Runtime-ID Boundary

**Status:** Amended
**Amends:** ADR-047, ADR-047-amendment-2026-04-20, ADR-047-amendment-2026-05-01
**PR:** #429 (`work/vexcoder-remove-tagged-xml-fallback`)

## Amendment

### Duplicate tool-call cards in the TUI

After the ingress normalization changes from ADR-047-amendment-2026-05-01, every tool call traversed two `ConversationStreamUpdate::BlockStart` emissions:

1. `RuntimeSignal::TranscriptBlockStart { block: StreamBlock::ToolCall { id: source_id, .. } }` — emitted with the server-assigned source ID (e.g. `toulu_01...` or `toulu_tagged_<n>`).
2. A re-emit inside the `ToolCallArgumentsDelta` handler — emitted with the runtime ID generated by `generate_tool_call_id()` (e.g. `tx_...`) once the accumulated arguments became parseable.

Source ID and runtime ID are different by construction. The TUI duplicate-check in `model_update.rs::StreamBlock::ToolCall` matches by `existing_id == id`, so the second `BlockStart` failed to find the first entry and appended a fresh `PulseEntry::ToolCall`. Each tool call rendered as two cards: one stuck at "Pending" with the in-progress placeholder ("Mapping adjacent sectors…") and one in the correct terminal state. Subsequent `ToolCallArgumentsUpdated` events updated the runtime-ID entry's input but left the source-ID entry frozen.

### Fix: single BlockStart, runtime ID only (commit 1a6b841)

The `TranscriptBlockStart { ToolCall }` arm in `send_message.rs` no longer calls `emit_stream_block_start_update`. It only:

- updates `saw_native_tool_call_block` (XML-only-protocol detector from ADR-047-amendment-2026-05-01), and
- pushes the block index onto `pending_tool_block_indices` so the matching runtime ID can be paired with it later.

The `ToolCallStarted` arm now performs the single `BlockStart` emission, using the runtime tool-call ID and the materialised arguments:

```rust
if let Some(index) = pending_tool_block_indices.pop_front() {
    tool_block_indices.insert(tool_call_id.clone(), index);
    block_tool_call_ids.insert(index, tool_call_id.clone());
    self.emit_stream_block_start_update(
        index,
        StreamBlock::ToolCall {
            id: tool_call_id.clone(),
            name: tool_name.clone(),
            input: arguments.clone(),
            status: ToolStatus::Pending,
        },
        stream_delta_tx,
    );
}
```

The redundant re-emit inside the `ToolCallArgumentsDelta` handler is removed. `ToolCallArgumentsUpdated` continues to refine `input` and `name` on the same runtime-ID entry as more delta chunks arrive.

### Consequences

- Exactly one `PulseEntry::ToolCall` per tool call in the TUI's `task_doc`. The duplicate-card and stale-status rendering artifact is gone.
- `ToolCallArgumentsUpdated` always finds the entry it refers to, because the entry now uses the same runtime ID that the update carries.
- Source IDs (`toulu_*`, including the synthesized `toulu_tagged_*`) are no longer surfaced to the UI. They remain inside `send_message`'s bookkeeping (`block_tool_call_ids`, `tool_use_positions`) where the source-ID prefix is still meaningful for the structured-round protocol detector.
- `TranscriptBlockStart { ToolResult }` is unaffected and continues to emit immediately.
