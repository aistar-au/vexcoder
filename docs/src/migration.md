# Migration Guide

This document covers migration from pre-ADR-022 vexcoder deployments to the
current ADR-022/ADR-024 configuration model. It is the canonical source of
truth for the variable rename table; `vex migrate config` is a convenience
generator that must match this document exactly.

---

## Legacy variable to current variable mapping

| Legacy variable | Legacy value | Current replacement | Notes |
| :--- | :--- | :--- | :--- |
| `VEX_API_PROTOCOL` | `anthropic` | `model_protocol = "messages-v1"` | |
| `VEX_API_PROTOCOL` | `openai` | `model_protocol = "chat-compat"` | |
| `VEX_STRUCTURED_TOOL_PROTOCOL` | `on` | `tool_call_mode = "structured"` | |
| `VEX_STRUCTURED_TOOL_PROTOCOL` | `off` | `tool_call_mode = "tagged-fallback"` | |
| `VEX_MODEL_URL` | full endpoint path | `model_url` | Strip `/v1/messages` or `/v1/chat/completions` suffix |

These are vexcoder's own pre-ADR-022 variable names. No third-party SDK
variable names are mapped. Migration from third-party tooling is the
operator's responsibility.

---

## Using `vex migrate config`

`vex migrate config` reads the legacy variables from the environment and
writes a `.vex/config.toml` fragment to stdout. It is non-destructive.

```sh
# Preview
vex migrate config

# Write to file
vex migrate config > .vex/config.toml

# Append to existing config
vex migrate config >> .vex/config.toml
```

Example output when `VEX_API_PROTOCOL=anthropic VEX_STRUCTURED_TOOL_PROTOCOL=on`:

```toml
# generated by vex migrate config
# apply this fragment to .vex/config.toml or ~/.config/vex/config.toml
model_protocol = "messages-v1"
tool_call_mode = "structured"
```

## Configuration file locations

vexcoder resolves configuration from five layers (highest priority wins):

| Priority | Source | Path |
| :--- | :--- | :--- |
| 1 | Environment variables | `VEX_*` as defined in ADR-022 |
| 2 | Repo-local config | `.vex/config.toml` (nearest ancestor `.vex/`) |
| 3 | User config | `~/.config/vex/config.toml` (XDG) or `~/.vex/config.toml` |
| 4 | System config | `/etc/vex/config.toml` |
| 5 | Compiled defaults | Inline defaults |

TOML key names mirror `VEX_*` variable names in snake_case. `VEX_MODEL_TOKEN`
is never read from any config file. It remains environment-only.

## Project instructions file

vexcoder searches for a project instructions file at session start in this
order: `.vex/AGENTS.md`, `AGENTS.md`, `.vex/PROJECT.md`. The first file found
is read and prepended to the system prompt within the configured token budget
(`VEX_MAX_PROJECT_INSTRUCTIONS_TOKENS`, default 4096 estimated tokens).

If the file exceeds the budget, it is skipped and a warning is written to
stderr. The session continues. A budget overflow does not fail startup.

The loaded path is shown in the TUI session header as `inst:<path>`, or
`inst:none` when no file was found.

---

## Notes on `VEX_MODEL_TOKEN`

`VEX_MODEL_TOKEN` must never appear in any config file at any layer. Any
config file containing a `model_token` key is rejected at load time with a
diagnostic naming the file. Set the token via the environment only:

```sh
export VEX_MODEL_TOKEN="your-token-here"
```
